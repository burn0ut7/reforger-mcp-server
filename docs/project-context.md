# Project context and packed/unpacked sources

Maintainer note: `.temp/tests/` contains optional, disposable local harnesses, excluded from public downloads. Commands below require those retained harnesses; historical evidence is not shipped or regenerated by a build.

`workbench_project_context(processId)` observes the running editor's native project owner on its main thread. It does not infer the project from a launch request, command line, title, or the newest folder. The current supported profile is Workbench 1.8.0.13 / Qt 6.8.3; it uses the existing native dispatcher, without a script adapter, Play, or UI traversal.

## Workflow

1. Obtain the intended process ID from `workbench_status`.
2. Call `workbench_project_context(processId)`. The default `scope: loaded` reports loaded addons, the current project file, their source locations, on-disk dependencies and local script-module declarations. `scope: available` or `all` includes the editor's available addons. `query` filters GUID, ID, title and project path. Page with `offset`, `limit` (1–100), and the returned `projectToken` on the same connection.
3. Call `pak_prepare(projectToken)` to prepare **both PAK and loose files** in the observed loaded-addon roots. This explicitly replaces the active catalogue's source selection. `includeAvailable: true` includes available addons; optional `addonGuids` selects specific observed GUIDs within that scope. Selecting an available addon does not load it into the editor. Omit the token to prepare the configured roots instead.
4. Use the existing `pak_status`, `pak_search`, `pak_search_text`, `pak_read` and `pak_extract` tools. In project mode, `source` is the addon GUID. `pak_search` exposes `storage: pak` or `loose`; exact entry IDs retain separate packed/loose copies of the same virtual path. Pass `revision` when paging.

The historical `pak_*` tool names are retained: there is one catalogue, scanner and reader pipeline, with the existing PAK decoder and explicit loose-file reads. There is no separate project search backend. Extraction writes byte-preserving copies into managed exports, never back into addons.

The engine's current project and the intended writable addon are different concepts. The observed base project can remain current while another addon is loaded. Select the intended addon by its observed GUID; the server does not assume the last loaded addon is current or writable. `root` is the directory containing the native owner's project file. `mountedRoot` is present only when the native filesystem successfully resolves `$ID:` to a physical path. Packed addon roots can legitimately lack that resolution. No write-permission claim is made.

## Offline configured sources

For source access without a running Workbench, explicitly configure roots:

```json
{
  "dataDirectory": "%LOCALAPPDATA%/ReforgerMcp",
  "pakDirectories": { "addon": "D:/Mods/MyAddon" },
  "unpackedDirectories": { "addon": "D:/Mods/MyAddon" }
}
```

The same label in both maps must name the same root. A root in `pakDirectories` contributes archives recursively; a root in `unpackedDirectories` contributes loose files recursively, excluding `.pak` files and `.git`/`.svn` directories. Set both for a mixed addon, only `unpackedDirectories` for a loose addon, or only `pakDirectories` for archive-only access. Paths use the existing configuration-relative/environment-variable rules. Configured sources are disk inventories, not evidence that Workbench loaded them.

## Provenance and freshness

Project observations distinguish loaded from available. `currentProject` is copied from the same owner/index used by `Workbench.GetCurrentGameProjectFile`; loaded/available records correspond to `GameProject.GetLoadedAddons` and `GetAvailableAddons`. Native enumeration order is preserved as an observation, **not asserted as resource or script override precedence**. Duplicate GUIDs at different locations prevent ambiguous project preparation.

`.gproj` content is strict UTF-8, bounded to 4 MiB and 64 nesting levels. Parsed identity is checked against the native identity. Dependencies and module paths are **local on-disk declarations**, not inherited/effective configuration or proof of a successful compilation. Their source hash and file path are returned. Empty/invalid dependency strings remain visible as `invalid_or_empty_declaration`. Unavailable, unsupported or mismatched project declarations are reported per addon; preparation refuses selected unavailable/mismatched declarations. Unsaved editor buffers are not indexed.

Each successful preparation creates a revision. Project-bound catalogues retain the observed process identity and complete native project-context fingerprint; queries reobserve that context and reject a changed/restarted/unavailable editor. Restarting MCP can reuse the saved catalogue only while the same editor context remains available. Tokens themselves are connection-local and bounded to the most recent 16 observations. Rejected selection arguments do not retire the current catalogue; once preparation begins, failure/cancellation invalidates it and keeps diagnostic evidence.

Every operation checks archive and loose-file sets, lengths and modification times. Loose `.c` and `.gproj` files are also rehashed, so same-size edits with preserved timestamps are detected. Selected loose reads verify the captured byte hash. Other loose files with unchanged size/timestamp are fully hash-checked when read, not on every metadata search. Packed archive hashes are recorded at preparation; the existing archive freshness contract is unchanged. An explicit refresh is required after working-file changes; refreshing also rehashes the selected archives. No stale catalogue is silently substituted.

Source roots cannot overlap the data directory; linked paths are rejected. In project mode, nested selected addon roots are separately inventoried rather than counted within their selected parent. File reads retain the existing 64 MiB limit, script mirrors 512 MiB, and catalogues two million entries; loose metadata supports sizes up to 2 GiB minus one byte. Binary files are discoverable/extractable within these bounds, but text reads do not convert binary resources. Invalid UTF-8 scripts are preserved and excluded from text search. Coverage and limits are explicit; there is no claim of a transactional filesystem snapshot during concurrent edits.

## Native ownership and validation

The adapter calls the project-owner accessor at RVA `1EA3F00`, copies the loaded (`+C8/+D4`) and available (`+D8/+E4`) arrays, and current index (`+120`) on the editor thread. Addon records supply ID/GUID/title/project-file strings at `+20/+28/+30/+38`. Physical mount resolution uses the same filesystem virtual method (`+140`) as `Workbench.GetAbsolutePath`. These are private ABI observations, protected by the existing exact binary hashes and code checks, not a public ABI. Counts and text are bounded; overflow rejects the observation without returning a partial context. The callback preserves no engine pointer after completion.

It writes a test-owned catalogue in that folder. The PAK fixture suite remains the regression for archive decoding, cancellation, extraction and existing source behavior.
