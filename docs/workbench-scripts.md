# Workbench script operations

Maintainer note: `.temp/tests/` contains optional, disposable local harnesses, excluded from public downloads. Commands below require those retained harnesses; historical evidence is not shipped or regenerated by a build.

Use the existing `workbench.executable` configuration. No scripted bridge, communication server, installed DLL, Java or Ghidra is required at runtime.

1. Call `workbench_script_status`; confirm the intended project with the capture tools. Window titles alone do not verify project identity.
2. Save source files and resolve dirty editor tabs/dialogs. Leave Workbench idle.
3. Pass the returned `processId` to `workbench_reload_scripts`.

`workbench_reload_scripts(processId)` performs one full validation/reload on Workbench's main thread. There is no action selector: Game and Workbench modules use the same routine.

The former `workbench_scripts` endpoint (including its `reload_game`, `reload_workbench`, `validate` and `open_script_editor` actions) is removed. Refresh the MCP tool list and use the new tool with `processId` only. Old tool calls fail instead of being silently converted into a reload. Standalone validation remains unsupported. Read-only accessibility remains for status, diagnostics and readiness checks.

Reload does not require focus, open menus or keyboard input. It works with Resource Manager and optional Script Editor/World Editor open. One Reload call stops embedded Play if needed, verifies that it stopped, then reloads; World Editor remains open. An unconfirmed Stop result returns `reload_not_started` and does not dispatch Reload; native exceptions retain their original error path and also prevent Reload. A process-wide mutex holds the entire Stop/Reload sequence against other native operations. Other editor types and unsaved tabs/dialogs are rejected. Native notification popups are allowed. The tested successful background reload left the foreground application unchanged; native error dialogs and user interaction can still affect focus. This is not a guarantee that Workbench never displays UI.

Reload is supported only for the exact Workbench **1.8.0.13** and Qt **6.8.3** binaries in the [native adapter profile](workbench-native-reload.md). Updated or modified binaries fail explicitly; there is no alternate reload backend. The Windows x64 server needs permission to read/write that editor process and create its native callback. No installed game files are patched.

## Results and recovery

For reload, `reloaded` means the full native routine returned success on the verified main thread. `reload_failed` means it returned false, which can indicate a validation error or editor veto; inspect native logs and `workbench_script_status`. The result includes thread IDs, elapsed time, temporary-allocation cleanup, and foreground observations sampled approximately every 5 ms. Sampling is evidence, not proof that no shorter transition occurred. Separate game clients are unaffected.

Accessible status diagnostics respect the UI's filters/expansion and may omit entries. Output is bounded to 32,769 characters; diagnostic output to 200 cells of 2,000 characters each. Historical status output is never treated as proof of a new operation. Native reload failures can be investigated in the current Workbench log; they do not trigger a separate menu-based validation.

Reload can reset runtime/editor state. The reload routine does not save or discard changes, accept dialogs, switch projects or stop play sessions. Only one matching configured process is accepted. A named mutex serializes cooperating servers' script operations; people and unrelated tools are not coordinated.

A native callback normally releases its two 4-KiB allocations, unwind registration and event handles after Qt destroys the queued event. If completion becomes uncertain, these resources stay alive rather than freeing executing code. A target-owned named event blocks further native reloads, even after the MCP server restarts. Inspect logs/dialogs and restart Workbench before trying again if the original server cannot finish cleanup. Process exit releases retained resources. There is no automatic retry or force-reset command.

Native execution has a 180-second completion deadline and 190-second outer wait; adapter threads have 5-second waits. After 500 ms an unfinished reload returns `pending` with `operationId`. Pending responses include bounded `dialogInspection` with observed prompt text and button IDs, or an explicit inspection-unavailable reason. Decide any response using the [window tools](workbench-windows.md#dialogs-during-pending-operations), then use the returned `poll` call on the same connection; no button is chosen automatically. Cancellation cannot undo a dispatched call. A blocked accessibility observation retains its operation lock until the provider returns if the caller times out.

## Code and verification

`src/ReforgerMcp/WorkbenchScriptTools.cs` defines the standard MCP interface; `WorkbenchSession.cs` owns read-only accessibility observations, readiness checks and routing to the hook; `NativeWorkbench.cs` owns all native reload offsets, ABI, dispatch and lifetime management. Launch and capture remain separate capabilities.

The archived `.temp/tests/ReforgerMcp.ScriptTests` targets the previous tool contract and must be updated before reuse. It used real MCP calls, exclusively named ordinary source files in a supplied loaded addon's `scripts/game` and sibling `scripts/WorkbenchGame`, and its current `console.log`. It checks changed loaded-module CRCs, initialization, deliberate invalid source, cleanup/recovery, unsupported binaries, operation claims and rejection of retired actions. Every actual reload checks foreground observations. Run only against an idle testable project, with a fresh evidence directory, Script Editor already open for diagnostic/capture tests, and another application in the foreground. A foreground precondition check stops before creating source or reloading if Workbench is already foreground. Test screenshots and log copies remain in that directory; production capture does not save screenshots to disk.


## Inline failure details and retained results

A `reload_failed` result includes `diagnostics`: `observed` with up to 40 error log lines (existing 24 KB entry budget), or `unavailable` with the reason. File/line locations remain in the original compiler messages. No extra tool or configuration is needed beyond existing `logDirectories` entries; their labels are arbitrary.

Before dispatch, the log reader examines the newest session of each configured source. Read-only Windows Restart Manager ownership must identify exactly one console file held by this Workbench PID and process start time. The reader records and later verifies its byte prefix, then requires exactly one new, completed reload cycle. Only errors up to that cycle's completion marker are included. Historical, replaced, ambiguous, incomplete, missing or inaccessible evidence is not substituted. Log scan work has a two-second cancellation budget per checkpoint/read phase; synchronous OS ownership calls cannot be interrupted by that budget. Diagnostics failure does not override the native reload result. There is no retry, background monitor, or extra log parser. Successful reloads do not repeat diagnostics.

The last 16 accepted native operation records retain their original results or errors in memory on this connection. Starting another operation no longer removes the immediately preceding result. At capacity, the oldest completed entry expires; polling an unknown/expired ID explicitly fails. No pending entry is evicted. A request refused because another operation is pending returns `blocked`, `dispatched: false`, and the exact original `poll` call. History does not survive server restart, and historical observations/action IDs keep their original expiry.
