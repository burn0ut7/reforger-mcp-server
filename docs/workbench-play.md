# World Editor Play sessions

Maintainer note: `.temp/tests/` contains optional, disposable local harnesses, excluded from public downloads. Commands below require those retained harnesses; historical evidence is not shipped or regenerated by a build.

Use the same C# MCP server with any compatible client:

1. Read `workbench_script_status` for the configured editor's process ID.
2. Call `workbench_play_status(processId)` to observe its native Play flag.
3. Call `workbench_play(action="start", processId)` or `workbench_play(action="stop", processId)`.
4. If the result is `pending`, keep the connection and poll `workbench_operation(operationId)`. Inspect and resolve dialogs with the [window tools](workbench-windows.md); never repeat a mutation to poll it.

The state check and normal native Play action run in one callback on Workbench's main thread. Start while playing returns `already_playing`; stop while stopped returns `already_stopped`. Neither invokes the toggle. Status does not open World Editor or load a world. This controls the embedded World Editor session, not separate game clients.

Start requires an existing saved, clean world. The native modified-state check uses the same conservative mask as world opening. Save or discard your changes explicitly before starting. The normal Play routine honors the editor's existing viewport/fullscreen, camera, layer and save-before-play settings. Save-before-play can invoke a save even for a clean world; the adapter does not change this setting. It runs the project's code and can access normal game services. Stop tears down runtime simulation and restores the editor world; it does not preserve runtime-only changes. No keyboard/mouse simulation or foreground prerequisite is used. Native windows can activate, especially with fullscreen settings or dialogs.

## Results and failures

| State | Meaning |
|---|---|
| `observed` | Status sampled `isPlaying` on the main thread. |
| `started` / `stopped` | The native Play flag changed to the requested state before the callback returned. |
| `already_playing` / `already_stopped` | The requested state was already present; no Play action invoked. |
| `transition_failed` | The normal native action returned without reaching the requested state. Inspect editor/logs; no automatic retry. |
| `world_unavailable` | No sole World Editor instance, or start found no saved world path. Nothing is created or saved to remedy it. |
| `editor_busy_or_unsaved` | Native start readiness rejected modified world state. |
| `incompatible_editor` | The observed instance did not match the supported native profile. |
| `outcome_unknown` | The callback did not establish a normal completion. Inspect before doing anything further. |

`wasPlaying` and `isPlaying` are point-in-time native observations. They are omitted when no state was observed. A Play flag does not establish scenario readiness, a player spawn, or error-free scripts. Results include expected/actual main-thread IDs, elapsed milliseconds, allocation cleanup and sampled foreground observations. These are execution evidence, not a universal guarantee about focus or game health.

Invalid actions/PIDs, process replacement, modal/disabled windows, incompatible binaries, active native claims and dispatch/cleanup errors are MCP errors. Resolve dialogs before status or mutations. Operations share the world/reload gate, cross-server mutex, target-owned claim, 500-ms pending response and 180-second native deadline described in [the native dispatcher](workbench-native-reload.md). Cancellation before acceptance prevents dispatch; cancellation after acceptance does not cancel native work. After timeout/disconnection, do not blindly replay. Retained claims require normal Workbench restart if the owning server cannot finish cleanup.

## Implementation and profile

`WorkbenchScriptTools.cs` owns the MCP contract; `WorkbenchSession.cs` owns process/readiness checks and serialization; `NativeWorkbench.cs` owns the single dispatcher and `EmitPlay`. No alternate backend or scripted bridge is introduced. The exact Workbench 1.8.0.13 and Qt 6.8.3 hashes remain required. Ghidra is only needed to research a new profile.

| Native contract | Current profile |
|---|---|
| World Editor lookup / descriptor / instance / primary vtable | Same as [world opening](workbench-worlds.md) |
| Play action wrapper | RVA `0x27F050`, `(worldEditor)`, void |
| Full lifecycle | RVA `0x27F070`, wrapper supplies bytes at `+0x68C` and `+0x684` |
| Embedded editor Play flag | World Editor `+0xA0`, virtual slot `+0x98` |
| Modified check | Embedded editor virtual slot `+0x70`, mask `0x1F` |
| Saved world path | World Editor `+0x120` -> manager `+0x50` |

The wrapper is connected to the native Play action. The full routine performs its normal readiness checks, resource selection, save policy and game/edit lifecycle. Its return is void, so the adapter samples the Play flag before and after, rather than interpreting a register as success. The application `+0x164E` guard can be set during Play: it continues to block world opening/reload but cannot block Play observation/stop. The separate reload guard at RVA `0x3DB65E5` still blocks these operations.

Local Ghidra evidence under `.temp/artifacts/native-index/queries/`: action wiring `c07150f7a3d44ec2bc456939cb083d90`, wrapper instructions `0355f18dfc0242dfb16ff470e3cb8276`, full lifecycle `8ddc0be9a4274ceb860972c53569ced6`, callers `2f2d1c344c8a4ac88454adf33caba1e2`. Global analysis reports warnings/errors; these individual decompilations completed without diagnostics. These artifacts are reconstructed evidence, not original source, and are not distributed.

## Validation

`.temp/tests/ReforgerMcp.PlayTests` exercises the real MCP transport, invalid actions/PIDs, pre-cancellation, shared claims, native status, two start/stop cycles, repeated-request no-ops, world-open rejection while playing, absence of World Editor, reopening afterward, modal Save As rejection/cancellation, fresh log deltas and screenshots. It uses the installed `MpTest_Basic.ent` world and leaves it stopped. Logs must independently show game-world initialization and runtime teardown/editor restoration. Every result checks main-thread execution and temporary-allocation cleanup. It records timings and the tested server hash without imposing an invented performance budget.

The initial source probe exposed a shared guard rejecting status/stop while Play was active. Failure evidence remains in `.temp/local/research/play-first-cycle.jsonl`; the corrected stop of that existing session is recorded in `play-stop-recovery.jsonl`. It was not recovered by toggling UI controls or restarting the editor. Test-world engine warnings remain in the raw logs; Play success does not certify their absence. Fullscreen settings, arbitrary project scripts, forced process loss and hung callbacks are not covered by the basic-world suite.

The packaged validation in `.temp/local/evidence/play-package-03/` passed 207 assertions. Two basic-world cycles measured native callback durations of 596/544 ms for start and 324/334 ms for stop; these are local measurements, not a latency guarantee. Earlier harness failures are retained in `play-source-01`, `play-source-02`, `play-package-01` and `play-package-02`: the harness initially expected a synchronous world-open rejection and immediate/stable dialog enumeration. It now polls pending results and refreshes changed read-only snapshots without replaying mutations. Modified-world rejection is inspected against the native guard, not exercised by introducing dirty user content.
