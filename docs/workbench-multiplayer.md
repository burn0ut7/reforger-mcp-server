# Dedicated server and Peer Tool

Maintainer note: `.temp/tests/` contains optional, disposable local harnesses, excluded from public downloads. Commands below require those retained harnesses; historical evidence is not shipped or regenerated by a build.

These three MCP tools operate the existing plugins in the open World Editor. They use the same native main-thread dispatcher as [Play](workbench-play.md), with the exact Workbench 1.8.0.13 / Qt 6.8.3 profile. Ghidra is needed only to research another binary version. No second launcher, scripted bridge, menu traversal or installed-script modification is involved.

1. Get the editor `processId` from `workbench_script_status`.
2. Read `workbench_multiplayer_status(tool="dedicated", processId)` and the corresponding `tool="peers"` status. Inspect the current world, executables, arguments, enabled peers and profiles.
3. Call `workbench_multiplayer(tool="dedicated", action="start", processId)`. Its normal **Start Dedicated Server** dialog opens. Use the [window tools](workbench-windows.md) to select **Run**, **Start only clients**, or **Close**, and resolve script authorization prompts. Current settings remain the defaults.
4. Poll `workbench_operation(operationId)` on the same connection whenever a tool returns `pending`. Do not repeat a launch to poll it. After dialogs finish closing, inspect status and logs: `invoked` proves dispatch, and a running process does not prove connection or player readiness.
5. To add the separate Peer Tool clients, call `workbench_multiplayer(tool="peers", action="start", processId)`. This sends only that plugin its normal startup event. It preserves its configured delay and peer options; it does not start an embedded Play session or another server. Delayed launches can raise authorization dialogs after the start call returns.
6. Stop each group using its own `tool` and `action="stop"`. Peer Tool stop cancels its delayed launch and ends its own clients. Dedicated stop ends its server and dedicated-tool peers. Inspect the returned stop state before changing settings or starting again.

The plugins assemble connection arguments themselves. Inspect the returned arguments and the server/peer logs to confirm the intended endpoint. Their default `-client` behavior was observed connecting to localhost port 2001; explicit parameters or different server configurations can change this. Use distinct peer profiles when both plugins would otherwise use the same profile suffix. The adapter never silently changes ports, profiles, peer count or saved options.

## Settings

`workbench_multiplayer_setting(tool, processId, field)` reads one live field. Add `value` and a meaningful `reason` to change it while the group is stopped. Values are strings, decimal integers, or `true`/`false`. These updates affect the loaded instance; the adapter does not write registry settings. Workbench's own dialogs may later persist the instance normally.

| Scope | Fields |
|---|---|
| Dedicated | `world`, `executable`, `profile`, `parameters`, `runPeers`, `maxFPS`, `peerExecutable` |
| Peer Tool | `executable`, `launchDelay` (seconds, 0–1000) |
| Both | `peerCount` (read only), `peer.INDEX.FIELD` |
| Peer fields | `title`, `enabled`, `profile`, `parameters`, `autoJoin`, `autoReconnect`, `disableTimeout`, `windowed`, `forceUpdate`, `noFocus`, `maxFPS`, `width`, `height`, `x`, `y` |

Indices are zero-based; the profile suffix is the order of enabled peers starting at 1. Only existing entries can be changed individually. `maxFPS` accepts -1 through 10000. Strings are bounded to 1023 UTF-8 bytes. An empty dedicated `world` uses the current world; a nonempty value must name a `.ent` resource. The field is available only for the direct-world configuration variant. JSON-config variants must be edited in the dedicated dialog. `workbench_multiplayer(tool="peers", action="configure", processId)` invokes Peer Tool's configuration dialog; the dedicated tool configures inside its start dialog.

## Processes, logs and uncertainty

Status reads the loaded settings through engine reflection and observes the plugins' own Windows process handles. It reports process IDs, creation times, executable paths, redacted command-line arguments and candidate log sessions. Settings themselves may contain sensitive parameters. Keep exported evidence private when it includes them.

Log roots come from `-logsDir`, or `${Documents}/My Games/<profile>/logs`; absent a profile, the default is `ArmaReforger`. Candidate `logs_*` directories are selected within 15 seconds of process creation. This is a candidate association, not proof: check the console's startup header, endpoint and connection events. Add desired roots to `logDirectories` to use [console log tools](console-logs.md). The example configuration includes default server and two PeerPlugin roots; adapt these to the observed profiles. Existing logs remain after stop.

`processes_running` means at least one observed or tracked process remains. A partially running group is not repaired or duplicated by another start. `launch_unsettled` means an accepted launch has not been explicitly stopped, including a delayed launch or cancelled dialog. Claims in `%LOCALAPPDATA%/ReforgerMcp/MultiplayerClaims` survive MCP reconnect and are tied to the editor's PID and creation time. Do not delete a claim to bypass uncertainty.

Stop records original process identities before invoking the plugin. It verifies those identities after the plugin returns, even when the plugin clears its handles. `stop_unsettled` and `survivingProcesses` identify a failed or not-yet-finished stop. In particular, denying KillProcess authorization can leave clients alive after the built-in plugin clears its references. There is no alternate kill implementation: inspect and resolve those processes before continuing. A repeated stop can settle a completed exit, but cannot reacquire a reference discarded by the plugin.

The dedicated plugin closes its OS server handle without clearing its script field. The adapter clears that stale field only when Windows proves it no longer identifies a process, on the main thread during mutations. `closed_handle` observations distinguish that case from access failures; they alone do not prove a previous process exited. A stopped status describes observed ownership and tracked identities, not an inventory of every game process launched outside MCP. Processes never observed before an external UI action discarded their handles cannot be recovered from that handle.

Resolve modal dialogs before starting another operation; Qt action completion can precede dialog teardown. Native dispatch and cleanup uncertainty retain the shared native claim and block replay. Follow [dispatcher recovery](workbench-native-reload.md), rather than blindly launching again.

## Implementation and evidence

`WorkbenchMultiplayerTools.cs` defines the thin MCP interface; `WorkbenchMultiplayer.cs` owns lifecycle/claims and configuration policy; `MultiplayerProcess.cs` observes process identities/arguments/log candidates; `NativeWorkbench.cs` owns reflected access and native events. Each aggregate operation hashes immutable open binary files once and still verifies callable code in the live process on every dispatch.

The native plugin menu is World Editor `+0x78`, with plugin array `+0x60` and count `+0x6C`. Exact reflected class names select `SCR_DedicatedServerPlugin` and `PeerPlugin`. Run/Configure/Ended/Started wrappers are RVAs `0x2EAE90`, `0x2E9060`, `0x2E9510`, `0x2E9770`. Peer startup uses mode `Server localhost + PeerTool`. Field reflection is `0x1E9D100`, object resolution `0x1F6F0B0`, and engine string assignment `0x1F6EA40`. Arrays and process handles are not public writable fields. The callback reserves 48 bytes for shadow space plus two stack arguments, with matching unwind metadata.

Local Ghidra query evidence under `.temp/artifacts/native-index/queries/`: plugin lookup `f3e4c84dbde14faf9dc128138bfa5281`; Run `6fd301459d374b779cb0e4a4c4d3cc03`; Configure `3e5c88cd49e44781bb0539eb5c54bfdd`; Ended `9d2e1e5978a84133b2b165ed99c59c53`; Started `24ee08f9f6ad4da191f6b0e70c2c359b`; reflection `28c6468bb98246b28276c7251845e588`; string assignment `668cf98d835448469acd21f0a978b32c`; KillProcess wrapper `734e62b1a99645a18259feb919798a4c` and native close behavior `f040c42b4d584d5b89e2c8eb26d5f374`. These are reconstructed evidence, not original C++ or a supported public ABI. Global analysis has warnings/errors; inspect individual results and live validation. These local artifacts are not distributed.

`.temp/tests/ReforgerMcp.MultiplayerTests` exercises real MCP discovery, guards, live settings, dedicated server plus two clients, a third client from Peer Tool, connection events from both sides, independent stop ownership, repeated start/stop, delayed-start cancellation and restoration of settings. It uses `MpTest_Basic.ent` for connectivity; that test world has no playable game mode and does not establish successful player spawning. Earlier failures and raw evidence remain under `.temp/local/evidence/multiplayer-*`. Native Play regression tests cover the shared dispatcher. Arbitrary scenarios, remote network/firewall setup and forced editor loss are outside this local connectivity test.

The source suite (`multiplayer-source-04`) and packaged suite (`multiplayer-package-01`) each passed 57 checks. Shared-dispatcher Play regression (`play-multiplayer-package-03`) passed 209 checks, including world reopening and modal-dialog recovery. Earlier failures are retained: source runs 01–03 exposed stale/closed handle handling and modal teardown timing; Play runs 01–02 encountered an occupied analysis store and a minimized screenshot target. The existing session was stopped through the native Play tool before rerunning. These are local results, not a latency or arbitrary-scenario guarantee.
