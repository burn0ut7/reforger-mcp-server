# Official Reforger wiki capture and search

Maintainer note: `.temp/tests/` contains optional, disposable local harnesses, excluded from public downloads. Commands below require those retained harnesses; historical evidence is not shipped or regenerated by a build.

The official Bohemia Community Wiki is the primary authority for documented concepts, purpose and intended modding workflows. Installed game declarations and native compiler behavior establish version-specific callable APIs. Wiki examples are not automatically compiler-verified.

“Wiki data” here means the [Bohemia Community Wiki](https://community.bistudio.com/wiki/Category:Arma_Reforger/Modding), not the separate Wikidata project.

## Capture boundary

The same C# `WikiStore` owns indexing, provenance, search and reads for both explicit inputs: official API capture (`wiki_prepare`) or saved browser DOM (`wiki_import_browser`). There is no automatic switch between them. Search/read/status make no network requests.

The browser pass on 2026-10-20 followed the Modding category and all observed descendant categories/linked Reforger articles: 298 visits consolidated to **292 distinct pages (250 articles, 42 categories)** and **1,066 code blocks**. The saved-link audit found no unresolved in-scope links in that discovered graph. This does not establish coverage of uncategorized pages unreachable from those links. Images, videos, attachments, external sites and original wikitext are not part of the browser capture; their links remain available. Full rendered HTML includes inline content and rendered templates but is not a self-contained offline visual mirror.

The API mode uses the official `https://community.bistudio.com/wikidata/api.php`. It enumerates the complete Arma Reforger namespace (5050), including pages absent from categories, and walks `Category:Arma Reforger` recursively. Starting above Modding also captures Reforger support, content and server documentation. Category traversal accepts only `Category:Arma Reforger` and its slash descendants; directly categorized main-namespace articles are included as shared Reforger documentation. Unrelated categories, other game namespaces, talk/user pages and file pages are excluded and listed.

This is an explicit discoverable boundary, not a claim that arbitrary uncategorized/shared pages elsewhere have been found. Links, image names, external links and template dependencies are inventoried without crawling external sites or unrelated articles. Media binaries, downloadable attachments, separately hosted script API documentation, revision history and template source are not downloaded. HTML contains rendered template content. A page's original source revision is pinned; template rendering can reflect capture-time template versions. Capturing a changing website is not an atomic upstream snapshot.

## Use

### Coordinated modding research

`research_mod(query, source?, limit=2)` is the question-oriented starting point. For example, ask for `creating a user action`, `multiplayer replication`, or `optimise scripts`. It uses the existing wiki and PAK stores; no additional index, model service, network request or automatic preparation is involved.

The response contains up to two pages by default (maximum five), up to three excerpts of 400 Unicode characters per page, and up to two page-level `enfusion://` links per page. Each page has one revision-pinned section-reading call. Applicable warning callouts take priority over extra examples; `warningsOmitted` counts further applicable warnings. This is lexical discovery, not a complete implementation plan or proof that every prerequisite was identified. Resource-manager links accept `~<addon>:<path>` for any addon and retain the declared addon name. Installed candidates match paths only; the result does not verify addon identity or infer override precedence.

Ranking uses whole normalized words, corpus term rarity, saturating frequency, title/heading fields, coverage of the question and terms appearing together in a passage with its title/heading context. Common question words, spelling/plural variations, scripting/script, set up/setup and add-on/addon are normalized; camel-case and underscore names remain intact. Two limited terminology bridges are exposed in `expandedTerms`: optimisation to performance, and initialisation to instantiation. They are documentation vocabulary, not aliases for callable APIs. Literal `wiki_search` retains all-term substring matching and alphabetical order; `kind=text` includes warning/note prose.

Supported Script Editor links supply script paths and historical line hints. Resource Manager links for `~<addon>:` supply resource paths. Link selection favours filenames matching the query, then identifiers literally present in selected excerpts, then matching path terms. Links remain page-level references, not proof that an excerpt uses a particular file. The PAK owner matches paths case-insensitively against its prepared catalogue, preserving separate archives and sources. It returns up to two candidates per path, the total count, and a `pak_search` call to inspect more. Script candidates lead to `pak_read`; binary resource candidates lead to explicit `pak_extract`, which saves bytes without converting them. Nothing is extracted or opened by research itself.

Wiki line numbers are never used as current line locations. A file-path match does not verify a symbol, API signature, resource GUID or override precedence. Unsupported/malformed links remain labelled and are not repaired. Omitted pages and links are counted; use `wiki_search` and `wiki_read` for exhaustive exploration. Empty results mean no matches under this lexical rule.

Both stores share `dataDirectory`. With a prepared PAK configuration, import the saved browser capture using that same configuration. Wiki-only research works too: installed data is explicitly `unavailable` when not configured/prepared. Stale PAK data is never substituted; the response reports its failure reason. Invalid source names fail the request. Wiki failure prevents research and requires explicit recovery through `wiki_status` and the selected capture/import route.

`wiki_read(view="section", passageNumber=...)` reads the selected passage's section, nested subsections, and preceding global/ancestor warning callouts. It stops before the next sibling section, including siblings with identical titles. `offset` and `nextOffset` page this selected collection; repeat the same page ID, passage number and revision. The default limit is eight blocks. Both `section` and `passages` cap returned text at 6,000 Unicode characters, with at most 4,000 per block, even if a larger block count is requested. A truncated block is explicit: retrieve it exactly using `view="passage"` and its number with character pagination. `nextOffset` advances through blocks, not through a truncated block's remaining characters.

Page-wide link/image inventories are omitted by default. Request `includeLinks=true` only when exploring those references. Section paths and table labels travel with passages; code bytes remain unchanged. Warnings are typed rather than detached icons. Table rows carry their column headers, merged-cell values and meaningful image alternatives; an empty cell is labelled `(empty)`, not inferred to mean false. This preserves textual table meaning, not visual layout or image pixels.

The extracted index is schema 2. A schema-1 index must be explicitly rebuilt through the existing browser import or API preparation route. Import accepts the old index only for change comparison; queries never silently reinterpret it. Reimporting the saved browser capture needs no website access. All pages can report changed when extraction changes, even though source hashes and upstream revisions are identical.

Real stdio checks cover tutorial, replication, prefab, optimisation, identifier, audio and initialisation questions; bounded section reading with prerequisites; installed declaration readback; invalid requests and unavailable installed data. Fixtures cover table spans, image alternatives, warning types, heading ancestry, code labels and full Unicode reconstruction. PAK regression checks cover duplicate paths, absent paths and stale archives. These checks do not compile or run a mod.

Use the same `configuration.json` with your own data directory. For wiki-only use, keep `dataDirectory` and remove the optional installation settings shown in `configuration.example.json`. Start the server normally, call `wiki_status`, then explicitly `wiki_prepare`. Preparation may take many minutes and the client must allow a long-running call. Standard MCP cancellation stops it. A standalone capture uses:

```text
ReforgerMcp --config configuration.json --prepare-wiki
```

For an already completed browser capture, explicitly choose the import instead:

```text
ReforgerMcp --config configuration.json --import-wiki-browser <capture-directory>
```

Or call `wiki_import_browser(captureDirectory: "<absolute path>")`. The import is entirely local. It verifies HTML hashes, complete documents, Reforger namespace scope, revision IDs/permalinks, duplicate consistency and the manifest's completed traversal/resolved failures. It saves the full rendered HTML and indexes only the article content. Inputs remain intact. Import does not prove the capture's declared scope is exhaustive: audit discovered links separately.

An import reports `added`, `changed`, `unchanged` and `notInNewCapture` against the previous active snapshot. Changes compare page revision, normalized extracted content and source format, so a changed template can be detected even when a page revision stays the same. `notInNewCapture` is not proof of an upstream deletion. Extraction changes can also change the content hash.

The API mode sends serial, identified requests with at least 150 ms between them, a 90-second request timeout, a 32 MiB response limit and MediaWiki `maxlag=5`. Pagination tokens are exhausted; repeated tokens fail explicitly. HTTP/API failures and warnings stop the capture; there are no retries or substitute sources. A blocked/challenged API requires access to be resolved before another API capture. Do not bypass challenges.

Each refresh retires the active index immediately. Success publishes a new snapshot atomically; failure/cancellation leaves wiki search unavailable. Old snapshots and failed response evidence remain on disk but are not silently served. A process interrupted during capture reports `interrupted` after restart. Use only one server process for a data directory.

Queries:

| Need | Tool arguments |
|---|---|
| Find a workflow | `wiki_search(query: "replication", kind: "text")` |
| Find sample code | `wiki_search(query: "RplRpc", kind: "code")` |
| Browse categories | `wiki_search(kind: "category")` |
| Find page titles | `wiki_search(query: "Script", kind: "title")` |
| Filter direct membership | `wiki_search(category: "Category:Arma Reforger/Modding/Scripting")` |
| Read a hit | `wiki_read(pageId: <returned ID>, revision: <returned revision>)` |
| Read its surrounding section | `wiki_read(pageId: <ID>, view: "section", passageNumber: <number>, revision: <revision>)` |
| Explore page links/images | `wiki_read(pageId: <ID>, limit: 1, includeLinks: true, revision: <revision>)` |
| Inspect saved source | `wiki_read(pageId: <ID>, view: "source", revision: <revision>)` |
| Retrieve a complete long example | `wiki_read(pageId: <ID>, view: "passage", passageNumber: <number>, limit: 4000, revision: <revision>)` |
| Retrieve complete saved source | `wiki_read(pageId: <ID>, view: "source-text", limit: 4000, revision: <revision>)` |

Search is deterministic case-insensitive all-term matching within one passage, not semantic or symbol resolution. Category filtering is exact direct membership, not descendants. `kind: all` searches headings, prose and code; title and category searches return page entries. Empty query browses. Pages are sorted by title and passage order. Follow `nextOffset` with the same snapshot `revision`; changed revisions are rejected. `offset` is zero-based and `limit` is 1–100 for result lists. Preview text above 4,000 characters is explicitly truncated. For full text, the `passage` and `source-text` views page Unicode scalar values (not bytes or UTF-16 code units), with limit 1–4,000. Concatenate their `text` chunks while following `nextOffset`; this preserves code whitespace and long lines without relying on local filesystem access.

## Stored evidence and integrity

Under `dataDirectory/wiki/<snapshot-revision>/`:

- `responses/`: exact API response bytes and request URL, HTTP status, fetch time and SHA-256 sidecars, including failures.
- `<pageId>.wiki`: original wikitext for the recorded page revision.
- `<pageId>.html`: rendered HTML requested by that revision ID.
- `index.json`: page identity, source revision/time/hash, canonical and revision URLs, category membership, dependencies and ordered heading/prose/code passages.
- `progress.json`: captured/discovered counts and the last completed page.

For browser imports, `<pageId>.html` is the captured full DOM, `browser-capture.json` retains the operator's manifest, and `aliases.json` records consolidated duplicates. No `.wiki` file or API responses are invented. `sourceFormat: rendered-html`, `captureMethod: browser-dom`, `capturedAt` and the observed revision permalink accompany retrieval. `timestamp` retains the wiki's human-readable last-edited footer; it is not a parsed API timestamp. Browser template dependency metadata is unavailable (`templateMetadataAvailable: false`), although rendered template content is saved. Source reads return rendered HTML; treat embedded scripts as untrusted data and do not execute them.

`current.json` holds state and the index hash. Every query verifies the persisted index hash; source reads also verify the source hash. API response hashes are evidence records, not rechecked on every query. `wiki_status` reports capture time, never a claim that upstream is unchanged. Explicit preparation refreshes everything. There is no automatic cleanup; retain required snapshots and remove unneeded old directories only with the server stopped.

The server ships no wiki corpus. Site rights metadata is retained, but the live API returned empty rights text/URL; that does not establish permission to redistribute wiki content. Review applicable site terms before publishing a corpus.

## Browser capture and later updates

[capture-wiki-browser.mjs](../scripts/capture-wiki-browser.mjs) is an operator-side helper for an already connected browser tab with documented `goto` and read-only `playwright.evaluate` methods. It is not a server backend or a standalone browser launcher. In the browser tool's JavaScript session, load the module, call `createWikiCapture(tab, freshAbsoluteDirectory)`, then call the returned object's `next(10)` in bounded batches. Inspect progress between calls; stop for any challenge, failed page or unsupported category pagination. The helper never reads cookies or solves challenges. The normal root visit must be accessible.

Every new run uses a fresh directory. HTML is read in 60,000-character chunks, avoiding the browser tool's per-string output limit. The helper stores complete DOM and article HTML, source URLs, link inventory, footer/revision evidence, capture time and SHA-256. `index.json` contains schema 1, started/completed times, scope, pages, queue and failures. Each page entry references a 20-hex-character `.json` filename. Page JSON contains `url`, `html`, `htmlSha256` and `capturedAt`; revision identity, categories and article content are rederived from the saved HTML during C# import.

For updates, run a new explicitly requested browser capture, then import it and inspect the change counts. Old snapshots remain saved. This release performs a complete requested browser pass; it does not yet implement incremental online revision polling, scheduled refreshes or automatic browser control inside the MCP server. Merely reimporting old files does not check upstream.

## Validation

Run `dotnet build ReforgerMcp.slnx -c Release`, then:

```text
dotnet run --project .temp/tests/ReforgerMcp.WikiTests -c Release --no-build -- src/ReforgerMcp/bin/Release/net10.0-windows10.0.19041.0/ReforgerMcp.dll .temp/artifacts/wiki-tests-new
```

The test requires a fresh output directory. It exercises controlled MediaWiki responses through the same store and a separate real stdio server process: continuation, category cycles and scope, code/HTML extraction, provenance, search/read paging, hash corruption, stale tokens, failed refresh, cancellation and explicit recovery.

For the real saved browser corpus:

```text
dotnet run --project .temp/tests/ReforgerMcp.WikiTests -c Release --no-build -- browser src/ReforgerMcp/bin/Release/net10.0-windows10.0.19041.0/ReforgerMcp.dll <capture-directory> .temp/artifacts/wiki-browser-tests-new
```

This imports through real stdio, searches actual code/prose/categories/titles, compares code blocks against saved DOM on four representative pages, checks unchanged refreshes and stale tokens, and rejects incomplete, tampered and out-of-scope captures. The successful run is recorded at `.temp/artifacts/wiki-validation/browser-real-2.log`. Earlier failed runs and incomplete original captures remain available for diagnosis, including the large-string truncation and custom syntax-highlighter fixes. These checks verify the captured graph and representative extraction, not every external resource or universal upstream completeness.
