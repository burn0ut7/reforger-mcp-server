# PAK tools for mod authors

Maintainer note: `.temp/tests/` contains optional, disposable local harnesses, excluded from public downloads. Commands below require those retained harnesses; historical evidence is not shipped or regenerated by a build.

The C# MCP server provides offline asset discovery and a byte-preserving script/resource text store. The installed `.c` files are already Enforce Script source: exporting them requires archive decompression, not a decompiler. Generated `proto external` declarations do not contain the native implementation; use the separate `engine_*` tools to investigate native code.

## Set up and prepare

Set `pakDirectories` in your `configuration.json`; the single `configuration.example.json` shows the available settings. Each key is a source label and each value is a root searched recursively for PAKs. These are illustrative installation locations; choose your actual folders, on any drive:

```json
{
  "dataDirectory": "%LOCALAPPDATA%/ReforgerMcp",
  "pakDirectories": {
    "game": "D:/SteamLibrary/steamapps/common/Arma Reforger/addons",
    "server": "E:/DedicatedServers/Reforger/addons",
    "workbench": "D:/SteamLibrary/steamapps/common/Arma Reforger Tools/Workbench/addons",
    "addons": "${Documents}/My Games/ArmaReforger/addons"
  }
}
```

Launch the same MCP executable with `--config <absolute-configuration-file>`. Call `pak_status`, then explicitly call `pak_prepare` if unprepared or stale. Preparation is one awaited request; allow several minutes in the client timeout. Standard MCP cancellation stops work without publishing an incomplete revision. Installed archives remain read-only.

Remove roots for products you do not have installed: missing/inaccessible roots fail explicitly, while an existing empty root is reported with zero archives. A game-only user can keep just `dataDirectory` and `pakDirectories.game`. `sourceCoverage` reports archive, entry and script counts for every configured root. The roots cover nested `core`, `data` and downloaded mod folders automatically. Custom source labels are supported; these four labels are conventions, not special installation rules.

Every configured path (including native executable/Ghidra/JDK paths) supports:

| Form | Resolution |
| --- | --- |
| `D:/Other Library/.../addons` | Explicit absolute path; no Steam installation location is assumed. |
| `./packages` or `../game/addons` | Relative to the JSON configuration file, regardless of the client's working directory. |
| `%LOCALAPPDATA%/ReforgerMcp` | A variable from the server process environment; unset/empty variables fail explicitly. Custom variables work too. |
| `${Documents}/My Games/ArmaReforger/addons` | The Windows Documents known folder for the server account, including configured folder redirection. Override it if you use a custom game profile/add-on location. |

Use forward slashes in JSON or escape backslashes as `\\`. Drive-relative paths such as `D:folder` and root-relative paths such as `\folder` are rejected as ambiguous. Input/output containment checks run after resolution. Moving the configuration file can change relative locations; changing a variable can change the selected installation. Run `ReforgerMcp.exe --check-config <configuration-path>` before connecting to view the resolved locations and check configured input existence without creating a store. This check does not validate PAK format, runtime versions or write permissions. No registry/Steam scan, silent alternate path, or automatic install selection is used.

Preparation hashes every archive, catalogues entries, and stores readable text from supported script/resource formats in `<dataDirectory>/paks/<revision>/content.bin`. Identical bytes share storage; every source/archive entry keeps its identity. The manifest records hashes and byte ranges. `pak_read` and `pak_extract` still read/export exact selected source entries.

`pak_status` reports `supportedTextExtensions`, per-format `textCoverage`, searchable/excluded counts and bounded exclusion examples. Scripts, prefabs, layouts, configs, materials, worlds and layers participate. Binary/invalid UTF-8 candidates and entries over the 64 MiB read limit are explicitly excluded. Unsupported extensions remain path-searchable and readable/exportable within ordinary bounds. No guessed encoding, resource conversion, inheritance expansion or override precedence is applied.

Format 4 replaces script-only mirrors. Older catalogues require explicit `pak_prepare`; they are never silently searched as though resource contents were covered. The managed binary text store is not an authoring folder; read through the tools.

## Useful workflows

`pak_read` accepts the existing single `entryId` form or `reads: [{entryId, offset, limit}, ...]` (1–8 windows, defaults 0/20). Batch requests share one catalogue validation before/after and decode each distinct entry once. Limits total at most 200 lines; batch JSON is capped at 32 KiB. Results preserve request order with per-item identity/hash, line totals, continuation or errors. `limited=true` means the byte budget shortened one or more windows; an item can have zero lines and `nextOffset` equal to its requested offset. Continue needed windows singly or in a smaller batch. Invalid request structure, cancellation and stale catalogue state fail the whole batch. Single reads retain their existing response.

Successful search/read calls already check freshness. Reuse their revision instead of issuing a status call or preparation before each operation; explicit preparation remains necessary for stale/unprepared data or deliberate scope changes.

| Need | Requests |
| --- | --- |
| Find a class or example implementation | `pak_search_text(query: "class SCR_SoundManagerModule")`, then `pak_read(entryId: <returned ID>)`. |
| Find usages of a method | `pak_search_text(query: "GetSoundMapTag")`; inspect the returned source lines and context. |
| Explore several known terms together | `pak_search_text(queries: ["RplComponent", "RplRpc", "Replication"], source: "game")`. Use either `query` or `queries`. A batch accepts 1–8 queries, shares source/path filters, and returns up to three 180-character snippets per query. |
| Continue one batch query | Use `pak_search_text(query: <group query>, offset: <group nextOffset>, revision: <returned revision>)` with the same filters. Omit offset/limit on the batch itself. |
| Read a search hit in context | `pak_read(entryId: <file.entryId>, offset: <match.line minus 1>, limit: 20, revision: <returned revision>)`. Lines are one-based; offsets are zero-based. |
| Focus on a subsystem | `pak_search_text(query: "Sound", pathQuery: "scripts/Game/Systems")`. |
| Find a particular sample | `pak_search(query: "DoorRattle", kind: "sound")`. |
| List every sound | `pak_search(kind: "sound")`, following `nextOffset` with the returned `revision`. |
| Inspect a prefab, config or UI layout | `pak_search(kind: "prefab", query: <name>)`, then `pak_read` for readable text. Use `config`, `layout`, `material` or `audio-config` similarly. |
| Find explicit resource references | `pak_search_text(query: <path fragment or GUID literal>)`; literal text only, not the whole resource graph. |
| Find component examples | `pak_search_text(query: "LadderComponent", pathQuery: ".et")`; read relevant hits and their parents. |
| Find UI examples | `pak_search_text(query: "TextWidgetClass", pathQuery: ".layout")`; read the matching widget blocks. |
| Follow a config's resource reference | Read the config, then pass its referenced path to `pak_search`; archive IDs retain all matches. |
| Save an individual resource | `pak_extract(entryId: <exact ID>)`; open its returned file path. A separate provenance file accompanies it. |
| Limit by format or source | Add `extension: ".c"` or `source: "game"` to `pak_search`. `pak_search_text` also supports exact `source`: `game`, `server`, `workbench`, or `addons` with the example configuration. Filters intersect. |
| Focus on one downloaded add-on | Use `pak_search_text(query: <text>, source: "addons", pathQuery: <mod-folder-name>)`. Asset results also retain that folder in `archive`/`id`. |

`pak_search_text` returns `files: [{entryId, sha256, matches: [{line, text, truncated}]}]`, also inside each batch query group. This replaces flat `items`; file identity/hash appear once per page group. `total`, `offset`, `limit` and `nextOffset` still count matching lines, not files. A file can span pages; source copies remain distinct.

All search terms are literal, case-insensitive, separated by whitespace and ANDed. Content terms must occur on the same line. These searches do not parse Enforce syntax or prove that a native declaration is a supported callable mod API. Validate authored scripts in Workbench using the normal development workflow.

Asset pages use zero-based `offset` and `limit` 1–100; text read pages use a zero-based **line** offset. Returned line numbers are one-based. `nextOffset: null` means exhausted. Pass `revision` on subsequent pages, reads and extraction to pin the evidence. A changed revision fails explicitly. Lines longer than 2,000 characters are marked truncated; obtain complete bytes through `pak_extract`.

## Updates, recovery and boundaries

Every operation checks the configured archive set, lengths and modification times. A game update/addition/removal is reported as stale. Run `pak_prepare` to rehash everything and build a fresh revision. Full SHA-256 is captured during preparation; ordinary queries do **not** rehash every archive. Changes that preserve both length and modification time require an explicit prepare to detect.

Each explicit prepare retires the active pointer first. Failure, cancellation or a crash leaves no current catalogue; fix the reported cause and request preparation again. Old and incomplete revision folders remain for diagnosis, with no automatic fallback. Content searches verify selected readable byte ranges against their hashes. Missing/edited content fails explicitly; preparation creates a clean store. Status checks catalogue/source freshness, not every stored byte. Loose text candidates are rehashed during freshness checks, including resources.

One content file avoids opening a separate mirror file for every resource. Search scans identical stored content once per request, using up to eight workers (capped by available processors), and merges results in catalogue order. At most two documents larger than 4 MiB decode concurrently to limit overlapping large allocations. Workers retain counts; selected previews are read afterward, preserving paging without buffering every match. Hash and freshness checks remain mandatory. A batch shares one scan across up to eight queries. Results report `searchedFiles`, `excludedUnreadableFiles` and bounded exclusion examples for the selected filters. Do not edit the managed store.

Keep only one server per `dataDirectory`. Linked source/output paths are rejected. Destinations cannot overlap PAK input folders. Extraction writes to a fresh managed directory, never to a caller-supplied game/mod path. Old revisions and exports accumulate; stop the server and manually remove only unneeded derived folders, retaining the revision named in `current.json`.

Current format support is PAC1 with stored or zlib payloads (compression IDs 0 and 262). Metadata search can expose other compression IDs, but attempts to decode them fail explicitly. Each selected payload is limited to 64 MiB stored and decoded; the unique readable text store to 8 GiB; each FILE table to 64 MiB; each archive tree to one million nodes/64 levels and the catalogue to two million entries. Global catalogue/store bounds fail preparation; oversized text candidates remain explicitly excluded from content search.

Configured roots include all descendant PAKs, with linked paths rejected and directory traversal limited to 64 levels. Adding/removing a nested archive invalidates the catalogue just like a root-level change. New mod folders are picked up on the next preparation without editing the configuration. Loose files are included through explicit `unpackedDirectories` or project-scoped preparation; see [project context](project-context.md). Coverage identifies disk sources and, in project mode, observed loaded/available addons; it does not establish effective override precedence or every possible Reforger script.

Resource-database GUID resolution, semantic symbol indexing, inherited-value resolution, dependency graphs, audio playback/conversion, model/texture conversion and PAK writing are outside this version. WAV/SND extraction returns original bytes; `.snd` is not automatically converted to OGG. There is no Rust editor reconstruction or mod compilation orchestration.

## Verification

Build the solution with `dotnet build -c Release`. Run the real MCP test harness:

```text
dotnet .temp/tests/ReforgerMcp.PakTests/bin/Release/net10.0-windows10.0.19041.0/ReforgerMcp.PakTests.dll fixture <absolute-server-dll> <fresh-absolute-evidence-folder>
dotnet .temp/tests/ReforgerMcp.PakTests/bin/Release/net10.0-windows10.0.19041.0/ReforgerMcp.PakTests.dll sources <absolute-server-dll-or-exe> <fresh-absolute-evidence-folder> <your-configuration.json>
dotnet .temp/tests/ReforgerMcp.PakTests/bin/Release/net10.0-windows10.0.19041.0/ReforgerMcp.PakTests.dll sources-check <absolute-server-dll-or-exe> <fresh-absolute-evidence-folder> <your-prepared-configuration.json>
dotnet .temp/tests/ReforgerMcp.PakTests/bin/Release/net10.0-windows10.0.19041.0/ReforgerMcp.PakTests.dll workflow <absolute-server-exe> <your-prepared-configuration.json> <fresh-absolute-evidence-folder>
```

The workflow check exercises batched exploration, exact source reads, continuation, and active batch cancellation/recovery through MCP. It uses prepared data and does not refresh it. Batches keep the existing mirror format and per-script hash verification. Their response cap is 24 snippets and 4,320 snippet characters; query text, provenance and JSON escaping are additional. This is not a strict token cap. Independent queries benefit from sharing a scan; investigations whose next query depends on the previous answer still use successive calls.

`fixture` needs no game installation. It creates test-owned archives in folders with spaces and Unicode names and tests variable/config-relative resolution, raw/zlib reads, checksums, bounds, invalid paths, duplicate identities, non-UTF8 source, stale/mutated data, repair, failed refresh and restart.

`sources` takes PAK roots from the supplied configuration, creates a separate test-owned store inside its fresh evidence folder, compares the complete archive set against a filesystem inventory, verifies every mirrored script hash, and exercises reads/extraction/content search in each source plus restart. `sources-check` uses the supplied configuration's existing prepared store without rebuilding it (sample extraction adds managed exports). Counts are derived from the supplied corpus; no username, drive, installed products, game version, script count or class name is assumed. Empty and asset-only sources are valid. Every MCP response is saved beside `summary.json` or `recheck-summary.json`. Earlier evidence below used the historical `real`/`multi` harness modes, now replaced by these configurable modes.

- Release solution build: zero warnings/errors. Packaged Windows executable: 67 fixture assertions, including actual MCP cancellation/busy handling and recovery (`.temp/artifacts/pak-package-fixture-01.log` and its response directory).
- Installed game 1.8.0.13: 35 assertions, 14 PAKs / 217,706 entries / 19,445 WAV/SND entries. - Full preparation took 57.99 seconds on this Windows machine, asset searches about 20–44 ms and full script searches about 5.2–5.4 seconds. A 45-sample, one-second process observation recorded a peak working set of 217,493,504 bytes (~207 MiB) during the preparation/search run; it was not a complete lifetime memory trace. Retained development failures: the first fixture harness omitted `InvalidDataException` from its expected-rejection catch; a cancellation test attempted to remove its test file before the server finished releasing read handles; and the first native regression launch passed an incorrect argument count. The harnesses/invocation were corrected, with passing reruns above. These failures did not modify installed archives. Failed fixture directories and initial native output remain alongside the passing evidence.

### Script search profiling, 2026-10-20

On the same four-source revision, a stage profile attributed 14.9 of 16.1 seconds to repeated path checks: 375,069 ancestor/file checks for 18,512 readable scripts. Checking shared ancestors once per request reduced this to 23,282 checks. Using one attribute lookup instead of separate existence and attribute lookups reduced the isolated scan further to 1.5–1.6 seconds. Reading, hashing and matching still run for every selected script.

Eight direct-owner workloads compared the previous packaged implementation against the optimized implementation: full-corpus symbol search, its second page, a class declaration, mixed-case method usage, a partial identifier filtered by game/path, a subsystem filter, downloaded add-ons and an absent term. Their complete result objects were identical, including totals, order, hashes, coverage and pagination. Full-corpus requests fell from 17.0–17.7 seconds to 1.9–2.6 seconds; narrower requests also improved. These are sequential local samples, not latency guarantees or MCP transport timings.

Post-workload process working sets were 574.5 MiB before and 601.6 MiB after; retained managed memory after collection was 251.6 MiB in both. These are endpoint samples, not peak-memory measurements. The change adds a request-scoped set of checked paths, with no persistent index, text cache, dependency or additional public tool.
