# Opening worlds in Workbench

Maintainer note: `.temp/tests/` contains optional, disposable local harnesses, excluded from public downloads. Commands below require those retained harnesses; historical evidence is not shipped or regenerated by a build.

## Entity creation and prefabs

`workbench_create_entity` creates one root entity in the active World Editor layer.
Supply the current `processId`, the exact `loadedWorld` as `expectedWorld`, a unique
ASCII identifier `name`, an `asset`, and `position: [x,y,z]` in world meters.
Optional `angles` are the engine's three Euler angles in degrees (default zero).
The asset is an entity class such as `GenericEntity`, or a GUID-qualified resource
such as `{7D52C517720EF2F5}Prefabs/Props/Industrial/BarrelMetal_01_blue.et`.
Bare prefab paths are rejected: live tests showed they can produce entities
without the intended prefab inheritance. The tool changes the world in memory;
it does not save it. `workbench_entity` observes whether a named entity exists and
reports the active layer, without selecting or modifying anything.

`workbench_save_prefab` exports a named entity using native `CreateEntityTemplate`.
Supply `processId`, `expectedWorld`, `name`, and an absolute new `prefabPath` ending
in `.et`. Its parent directory must exist. Use a writable addon mounted in the
project. Existing prefab files or metadata are rejected. A successful `exported`
result requires the native call to succeed, native resource-database acknowledgement,
and both the file and `.meta` containing a GUID-qualified resource name to exist.
Pass the returned `prefabResource` to
`workbench_create_entity` to place an instance. The export preserves the source
entity; it does not replace it with an instance, save the world, or alter scripts.
Metadata existence is not a guarantee of successful subsequent resource loading.

Names are 1–96 ASCII letters/digits/underscores, starting with a letter or
underscore. Paths/resource names are limited to 240 UTF-8 bytes. Positions and
angles contain exactly three finite floats. These bounds protect the native
call's buffers; there are no production addon names or test-world special cases.
World identity is checked on the editor thread immediately before the operation.
Creation rejects existing names, play mode, active edit actions and locked layer
hierarchies. The caller chooses the active layer in Workbench; parent/child
creation, property editing and game-runtime invocation are outside this scope.

The tools use the existing main-thread dispatcher and the exact supported binary
profile below. `WorkbenchEntities.cs` owns validation and the MCP contract;
`NativeWorkbench.Entities.cs` owns the calls into `WorldEditorAPIwb` (vtable RVA
`0x2D83608`): FindEntityByName `+0x98`, GetCurrentEntityLayerId `+0x238`,
BeginEntityAction `+0x38`, CreateEntity `+0x1D8`, EndEntityAction `+0x40`, and
CreateEntityTemplate `+0x1C8`. Layer locking uses the owning hierarchy check at
RVA `0x1A74310`. Creation brackets the owning API in an edit action. No script
bridge, menu traversal, button invocation, arbitrary address endpoint or alternate
implementation is involved.

Export also follows the native `ResourceManager.WaitForFile` wrapper: normalize
the absolute path into the mounted database namespace (RVA `0x1F6600`), then call
the owning acknowledgement wait (`0x31A780`, five-second bound). This pumps the
editor's normal events until the resource database recognizes the path. It is a
completion condition, not a fixed sleep or a second export attempt. The bounded
native small string occupies scratch bytes 1664–1957; world readback begins at
2048. A timeout or failed normalization leaves `resourceAcknowledged: false` and
returns `export_incomplete`, even if files were written. Inspect rather than retry.

Read `state`, not just transport success: `created`, `exported`, and `observed`
are normal outcomes. `creation_failed`, `export_failed`, `export_incomplete`,
`edit_action_incomplete` and `outcome_unknown` require inspection before any new
mutation. Other explicit rejections include `world_changed`, `world_unavailable`,
`incompatible_editor`, `editor_busy`, `entity_name_exists`, `entity_missing`,
`layer_locked`, `edit_action_rejected`, and `destination_exists`. Input/preflight
errors are MCP tool errors. An incomplete export can leave files; nothing is
silently deleted or retried. Poll pending operations on the same connection with
`workbench_operation`, as for world opening.

### Validation and resource lifecycle

The persistent local fixture is `worlds/MCP_EntityTest.ent` in **Test Bullshit3**,
with `worlds/MCP_EntityTest_Layers/default.layer` and `Prefabs/MCPTests/` assets.
It inherits the base-game `MpTest_Basic.ent`; the user's existing `worlds/test.ent`
is separate. No addon scripts or game compilation changes are required.
The world was initialized as a subscene and subsequently saved by Workbench.

`.temp/tests/ReforgerMcp.EntityTests` takes seven arguments: packaged server DLL,
configuration, expected world path, absolute world file, prefab output directory,
GUID-qualified visible prefab, and a fresh evidence directory. It uses real MCP
calls for creation/export/placement, with existing window tools for normal
Save World and Undo/Redo validation only. It checks rejection paths, ordinary
placement undo/redo, prefab inheritance and coordinates, overwrite preservation,
and save/reopen persistence. Both ordinary placement and export followed immediately
by placement must pass Undo/Redo; the latter is checked after 2.5 seconds of normal
editor event processing to catch delayed history invalidation. It adds uniquely
named fixtures and leaves them saved.

Local evidence: `.temp/local/evidence/world-entities-20261021/acceptance07/` records
the final candidate's live checks on Workbench 1.8.0.13. Earlier runs and failures remain alongside it.
`acceptance04` exposed a test assumption about serialization: Workbench may group
entities sharing a prefab under `$grp`; the assertion now understands that form.

In `acceptance03` and `acceptance05`, export returned before the resource database
had acknowledged the new asset. The subsequent placement was initially recorded
in native history, but history was then cleared. `acceptance06` tested ordinary
placement only and was insufficient for acceptance; independent review blocked it.
Adding the owning acknowledgement step fixes the reproduced export→placement
Undo/Redo failure (`history-acknowledgement03` and `acceptance07`). A deliberate
intermediate diagnostic passed an unnormalized absolute path: its acknowledgement
timed out, demonstrating that a delay alone was insufficient evidence. The final
path normalization follows the official wrapper and requires a true acknowledgement.
The save-only baseline retained Undo, isolating the issue to the export workflow.

Export itself remains outside world undo. Workbench resource processing can clear
**preceding** edit history; the server reports this and does not suppress or replace
engine history. The completion boundary ensures the tested follow-up placement
begins after resource acknowledgement. This is not a guarantee against unrelated
future resource changes or user actions. Ghidra evidence for the official wrapper,
normalization and wait is indexed in the local `native.jsonl`; original API
declarations are in the installed `GameLib/generated/WorkbenchAPI/Modules/ResourceManager.c`.

## Opening an existing world

`workbench_open_world` opens one world in the already running configured Workbench. It shares the temporary native dispatcher with script reload. No project scripts, bridge, installed DLL, key presses, menu invocation or foreground prerequisite are involved. Java/Ghidra is only needed when researching a new binary profile, not at runtime.

Call `workbench_script_status` for the current `processId`, then:

```json
{"resourceName":"{A701424D70022078}worlds/MP/MpTest/MpTest_Basic.ent","processId":12345}
```

The PID above is illustrative. Use the observed PID. A relative resource path such as `worlds/MP/MpTest/MpTest_Basic.ent` or an absolute path accessible to the loaded project also works. The loaded project must include the resource's addon/dependencies. World Editor is created if needed; otherwise the clean current world is replaced. Opening can run the project's normal engine/script initialization. The tool does not start play mode.

Use `capture_windows` and `capture_screenshot` to inspect the resulting World Editor window. Those tools capture directly without activating it. World opening does not explicitly raise an existing editor, but Workbench's creation, progress or error UI may activate. Foreground samples are observations, not a universal guarantee against activation.

## Preconditions and results

- The exact Workbench 1.8.0.13/Qt 6.8.3 hashes in the [shared profile](workbench-native-reload.md) must match. Unsupported binaries fail before allocation; there is no fallback.
- Only Resource Manager, Script Editor and World Editor are supported. Resolve modal dialogs, disabled editors and dirty tabs first. A main-thread native check also rejects play mode and modified world state. Nothing is automatically saved or discarded.
- Supply one `.ent` path, at most 240 UTF-8 bytes, without control characters or semicolons. GUID resolution must also name a `.ent` file. Both its native resource path and filesystem-expanded path must fit 240 bytes. These conservative bounds protect fixed native path buffers; a short GUID does not bypass them.
- `opened` means the native full-open routine returned true on the expected main thread. `loadedWorld` is the engine's actual current path copied on that thread, not an echo of the request. It may use an addon prefix such as `$ArmaReforger:`.
- `open_failed` means creation, resolution, existence checking or the native load failed. A missing file is rejected before unloading an existing world. Other load failures can leave a different/empty editor state; inspect `loadedWorld`, logs and screenshots.
- `unsupported_world_path`, `editor_busy_or_unsaved` and `incompatible_editor` are explicit rejections, never success. A busy/incompatible result may lack a current-world observation. Input/readiness errors are MCP tool errors.

Results also contain `nativeResult`, completion/thread fields, elapsed milliseconds, approximately 5 ms foreground samples and `allocationsReleased`. A bounded copy of the current-world path is at most 2047 bytes. The normal accepted paths fit the smaller limits above.

The callback wait is 180 seconds and outer wait 190 seconds. Both script reload and world opening share one server gate, cross-server mutex and target-owned native claim. If a call is interrupted or times out, inspect the editor; do not blindly repeat it. Retained claims/allocations require Workbench restart if the original server cannot complete cleanup. The world-opening routine never kills a native thread or automatically answers a dialog. After 500 ms it returns `pending` with `operationId` if unfinished; keep the same server connection, inspect/answer dialogs using [window tools](workbench-windows.md), then call `workbench_operation`. Request cancellation after acceptance does not cancel the native work. The last 16 native operations retain their original results/errors on this server connection; the oldest completed entry is evicted at capacity. Server restart clears history. Re-reading a result does not refresh its observations or action IDs. Script reload currently still requires World Editor to be closed.

## Code and binary profile

`src/ReforgerMcp/WorkbenchScriptTools.cs` exposes the small MCP contract. `WorkbenchSession.cs` owns process selection, read-only readiness observations and operation serialization. `NativeWorkbench.cs` owns the one dispatcher, temporary allocation lifetime and world-specific thunk in `EmitOpenWorld`. No generic address or memory-write endpoint is exposed.

For the shared exact Workbench binary, Ghidra established these RVAs:

| Item | RVA / field |
| --- | --- |
| Find module descriptor by name | `0x20EA70`, `(app, "WorldEditor")` |
| Open module through normal initialization | `0x20FEC0`, `(app, descriptor, 0)` |
| Descriptor instance count/getter | `+0x24` / vtable `+0xD8` |
| World Editor main vtable | `0x2BA8D78` |
| Embedded editor play/modified checks | object `+0xA0`, vtable `+0x98` / `+0x70` with conservative mask `0x1F` |
| ResourceName constructor | `0x1E35D50`, `(outResourceName, UTF8)` |
| Filesystem getter; resolve/existence | `0x1E90630`; vtable `+0x148` `(fs,path,out560,-1)` / `+0x150` `(fs,path,-1)` |
| Full World Editor resource open | `0x2832B0`, `(worldEditor, ResourceName*)`, low-byte bool |
| ResourceName content destructor / allocator | `0x269DC0` / global `0x3C7C260`, allocator vtable `+0x10` |
| Current world path | world editor `+0x120` -> manager `+0x50` |

The native full-open routine performs unload and load lifecycle work; the adapter does not call only the lower-level entity loader. Existing World Editor lookup uses the descriptor's instance getter, avoiding the generic open-module path's explicit activation of an existing window. ResourceName ownership is acquired/released using the engine's own constructor and reference-count/allocator convention. Path checks run before full open on the same GUI callback. Scratch regions are bounded within the data allocation.

Local Ghidra evidence: full open query `d421699b9d9d4b5c8e0601e529ca32b2`, module lookup `ae4ad33a49b94f5f8b191f924c2be2ea`, module open `2711e16004d34ad5995fef289081e067`, native ResourceName ownership `4dd9a17064bc4500801427fd234610e2`, and filesystem existence check `4811e3b033ae44fdbb576c90fd4bda23` plus instruction query `25760aa7eef24b3a9095249502f7f37e`. The existence call requires the third mount-selector argument `-1`; the inferred pseudocode omitted it, so its machine instructions are authoritative. Long-path instruction evidence is recorded in queries `1df0a0387a0045f7b9e0f0148bec9bae` and `b69014ea1fe84091b4c3409e60a92c5b`. These installation-specific research artifacts are not shipped. Reanalyze the complete lifecycle and ownership contract when updating the isolated profile.

## Verification

`.temp/tests/ReforgerMcp.WorldTests` exercises the real packaged MCP server: discovery, invalid input, stale PID, pre-cancellation, shared claims, two base-game worlds, missing-resource preservation, repeated opening, current native path, fresh log deltas, thread/cleanup results and direct screenshot capture. It requires a clean project including ArmaReforger and another application foreground, and leaves `MpTest_Basic.ent` open. It writes no addon files. It never forces focus or retries uncertain mutations. Native play/modified guards are additionally reviewed against Ghidra; the suite does not create unsaved user edits or force play/hung callbacks.
