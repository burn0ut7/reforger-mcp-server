# Component calls during Workbench Play

Maintainer note: `.temp/tests/` contains optional, disposable local harnesses, excluded from public downloads. Commands below require those retained harnesses; historical evidence is not shipped or regenerated by a build.

The C# MCP server exposes `workbench_runtime_status`, `workbench_runtime_inspect`, `workbench_runtime_prepare` and `workbench_runtime_invoke`. Protocol 2 supports typed arguments and return values on existing script components in embedded World Editor Play. It does not create runtime components, emulate player interaction or control separate game/server processes. Server and adapter must use the same protocol version; incompatible versions fail explicitly.

## Profile installation and NET API enablement

Open the intended project in the supported Workbench. Use `workbench_runtime_setup(action="status", processId=...)` to observe the **running editor's** mounted profile and NET API port. This observation works when NET API is off. Obtain the PID from `workbench_script_status`. Setup uses the same exact-binary native compatibility checks as other Workbench operations.

Set `workbench.runtimePort` in your server configuration to that observed port and restart the MCP connection after editing its configuration. Setup preserves the editor's port; a missing/mismatched client port rejects installation/enablement before mutation. Configure `logDirectories.workbench` as described in [console logs](console-logs.md).

Close World Editor and other editors, leaving Resource Manager and optionally saved Script Editor tabs. Run `workbench_runtime_setup(action="install", processId=...)`. It installs the server's embedded adapter at `<active-profile>/scripts/WorkbenchGame/ReforgerMcp/RST_Runtime.c`, enables NET API through the native owner, persists the enabled setting, reloads scripts when the current adapter is not already confirmed loaded, and verifies readiness. The managed file also includes the dedicated-plugin path correction documented in [multiplayer](workbench-multiplayer.md#managed-dedicated-launch-paths). No gameplay addon is modified. The profile is resolved through Workbench's filesystem, including custom profiles; no Documents-path guess is used.

The packaged command-line entry point and PowerShell wrapper use this same C# implementation:

```powershell
.\ReforgerMcp.exe --config .\configuration.json --setup-runtime status
.\scripts\setup-workbench.ps1 -Config .\configuration.json -Action install
.\ReforgerMcp.exe --config .\configuration.json --setup-runtime enable
```

`enable` turns NET API on in the running editor even if there is no listener; it does not reinstall or reload scripts. It preserves the port and unrelated settings. There is no registry-edit or UI-navigation fallback. Stop Play and resolve modal dialogs/busy editor states first. Unsupported binaries fail explicitly. The server connects only to `127.0.0.1` and verifies listener ownership before sending requests. Setup rejects an already occupied IPv4 port owned by another process. A bind failure/race remains a reported failure, never a guarantee that the operating system will provide a listener.

`ready` requires the enabled native setting, the configured port matching the editor port, a listener owned by the selected PID, successful built-in script-compilation status, the exact installed adapter hash, and a receipt-correlated live handshake matching its build and profile. `not_ready` includes the failing observation. The CLI exits 0 only for `ready`; it waits for pending operations and exits nonzero on blocked/failed verification. Installation files/settings may remain changed after a later reload or verification failure; inspect diagnostics before another explicit action. Setup never automatically retries a mutation.

Repeated installation preserves identical adapter bytes and skips reload when the current handler is confirmed loaded. The ownership record is stored outside script imports at `<active-profile>/ReforgerMcp/runtime-install.json`; upgrades retain prior managed sources under its `backups` directory. Unmanaged differing files, locally edited managed files, and linked installation paths are rejected without overwrite. Only this tool's dedicated file/metadata are managed. Remove any previously manually installed copy of `RST_Runtime.c` from development addons before migration; duplicate class definitions are compiler errors, not a reason to silently delete user files. Old experimental profile scripts are not imported or reused. The raw adapter source in the distribution is a build template; install through setup to stamp its identity.

This is a development execution surface: anyone with access to the Workbench NET API can call installed handlers. Keep that endpoint confined to your trusted development machine/network. The MCP server's loopback restriction is not an authentication mechanism for Workbench itself.

The existing native dispatcher controls editor entities, components, prefab export, Play and runtime setup. Live VM access is owned by the small Enforce adapter: it resolves live references and uses the engine's documented [ScriptModule](https://community.bistudio.com/wikidata/external-data/arma-reforger/EnfusionScriptAPIPublic/interfaceScriptModule.html) compile/call APIs. The C# server owns installation, configuration, process/listener checks, serialization, tokens, transport deadlines and MCP. There is one runtime executor. The native VM calling convention is not validated; no direct native invocation of arbitrary methods is shipped, and no editor UI traversal is used for runtime calls or setup.

## Workflow

1. Obtain `processId` from `workbench_script_status`. Create a named entity, inspect it and add your component with the entity tools. Export a prefab using `workbench_save_prefab`, and save the world normally.
2. Start Play with `workbench_play`. Check a fresh log interval to establish that the method did not run automatically.
3. Call `workbench_runtime_prepare(processId, entityName, componentType, method)`. Component and method names must be ASCII identifiers, up to 96 characters; entity names accept up to 240 UTF-8 bytes without control characters. Entity lookup uses the engine's named-entity lookup; use a unique name. Exactly one component assignable to the requested type must exist. Supply `arguments` as at most nine `{type,value}` objects, using int, float, bool, string or vector (`[x,y,z]`). Supply every declared argument, including optional ones. `returnType` accepts those same types or void (default, explicitly discards the result). The compiler checks the typed signature and public access. Successful invocation returns the supported value in `returned`. The temporary validation function is never executed and no ScriptInvoker instance is created.
4. Invoke the returned `targetToken` on the same MCP connection within 55 seconds. Preparation does not execute the method. Only one prepared call is held by the adapter globally; another preparation supersedes it. Tokens are single-use, including on transport failure. The adapter also expires them after 60 seconds and checks the original world, entity and component references immediately before the call.
5. Read fresh logs using `log_read`, locating `RST_MCP_BEGIN <receipt>` and `RST_MCP_END <receipt> invoked`. Check the method's output and intended game-state assertions between/after those markers. For the fixture, require exactly one `Hello world | <selected-name> | call=1` and none from the control entity.

Operations may return `pending`; poll `workbench_operation` on the same connection. Cancellation after acceptance does not cancel engine work. The TCP deadline is 15 seconds; timeout/disconnection after sending is uncertain, never permission to replay. A method can block, destroy objects, schedule effects or change external state. No rollback or exactly-once guarantee across process loss is claimed.

## Result meanings

| State | Evidence |
|---|---|
| `playing` / `not_playing` | Adapter sampled embedded Play state. Stopped access clears its prepared reference. |
| `prepared` | Existing target resolved and a temporary typed call compiled. It has not run. |
| `entity_missing` / `component_missing_or_ambiguous` | Target resolution rejected the request. |
| `unsupported_component` / `invalid_request` | Type or request contract rejected. |
| `compile_rejected` | Compiler rejected visibility/name/signature; diagnostic text and line are returned. |
| `stale_target` | Token, lifetime or original live reference no longer matches. |
| `invoked` | Synchronous `ScriptModule.Call` returned true. **This does not prove the method finished without script errors.** Check logs and game state. |
| `call_failed` | `ScriptModule.Call` returned false. Effects are not assumed rolled back. |

Transport/adapter absence, wrong listener ownership, changed process, malformed response and consumed client token are MCP errors. Errors after dispatch explicitly warn about uncertainty. Object references, arrays, remote authority and asynchronous effect completion are outside this version's contract. Arguments are inputs only. Enforce signature checking accepts out/inout methods, but their argument updates are not returned; only the selected ordinary return value is captured. Compiler checking is not universal method enumeration or a security sandbox.

## Live inspection

`workbench_runtime_inspect(processId, entityName)` observes the named live entity's identity, transform and paged ScriptComponent-derived components. Supply `componentType` to inspect reflected fields on exactly one assignable component. `offset` is nonnegative and `limit` is 1–64. Primitive int/float/bool/string/vector fields are read without invoking gameplay methods; their `value` is textual. Other types report `unsupported_type`, and strings exceeding 512 characters report `truncated`. No object graph or property getter is evaluated. Pages are not an atomic snapshot of changing gameplay state. Unnamed entities and arbitrary world-population enumeration are not provided by this interface.

Authoring inspection is separate: a prefab/config override does not describe changing live fields. Use fresh runtime observations after invocation to check effects. Return success still does not establish absence of script exceptions or completion of scheduled behavior.

## Evidence and limitations

`.temp/tests/ReforgerMcp.RuntimeTests` exercises real stdio MCP, native entity creation/component attachment, prefab serialization, world save, Play, missing/inaccessible/required-argument methods, selected-instance logging, token replay and stop/start invalidation. It leaves Play stopped and retains fixture entities/prefabs. Fixtures are in `.temp/tests/fixtures/runtime`; no fixture name is present in production behavior.

Initial evidence is preserved in `.temp/local/evidence/runtime-source-01`: a temporary compiled direct-call wrapper reported success but did not produce the component's output. Protocol 2 executes a compiled `RST_Invoke` wrapper which calls the actual component through the owning game module's named `Call`; the separate `RST_AccessCheck` function is validation only and never executed. The underlying direct-call linker behavior is not established, and that route is not used. `.temp/local/evidence/runtime-source-03` records the first complete successful run and exact server/adapter hashes. Later final evidence must match the final revision.

Signature experiments are retained in `runtime-source-04`, `runtime-source-05` and `.temp/local/research/runtime-signature-probes.jsonl`: temporary-module inheritance sees sealed imported methods; local `func` variables are unsupported; typed native `ScriptInvokerBase.Insert` correctly checks exact arity but intentionally permits discarded results. The final validator uses that last compiler check without executing or instantiating it. Temporary research handlers were removed from the addon before final testing.

`.temp/local/evidence/runtime-package-01/` records the packaged workflow: no automatic print during startup plus three seconds of Play, one Hello between matching markers, a silent method, compiler rejections, MCP log readback and stale-token rejection after stop/start. `RuntimeTests --transport` additionally checks fragmented responses, oversized frames, early EOF, missing handlers, wrong listener ownership and timeout, with no automatic retry.

The initial editor process displayed a resource-leak assertion while destroying game state during reload, before the first adapter was loaded or runtime invocation was attempted. It also recurred after a fresh-process workflow. Dialog and acknowledgement evidence remains in `.temp/local/research/runtime-dialog-*.jsonl` and `runtime-assertion-ack*.jsonl`. Restarting is not a fix; the cause is not established, and this resource-leak issue remains unresolved. The initial launch harness disposed its child process tree; its failure is retained in `runtime-source-02` and launch was repeated only after process absence was confirmed, using graceful MCP shutdown.

Historical protocol-1 production-code evidence is `.temp/local/evidence/runtime-package-02/`; independent reproduction is `.temp/local/evidence/runtime-review-01/`. Both end with Play stopped. Their acceptance files pin the server and adapter hashes. Transport failure results are in `.temp/local/evidence/runtime-transport/`. Runtime calls measured 1–8 ms locally in the primary packaged run; this is not a performance budget or a guarantee for arbitrary gameplay methods.

Protocol-2 final evidence is retained in `.temp/local/evidence/high-priority-20261021/independent-review/runtime-final35/`, including typed primitive results, escaping, live field readback, unsupported-field reporting and lifecycle checks. Its acceptance file pins server and adapter hashes. The independent whole-task report `report-final35.md` passes the documented feature contract with no remaining review blockers. This does not establish a fix for the separately recorded script-reload assertion.
